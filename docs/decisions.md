# 技术决策记录

## 为什么要自主实现，而不是直接封装第三方仓库

本机是 8 GB 显存的 RTX 5060 Laptop，内存 15.4 GB，且参考仓库依赖跨度很大：DocRes 要求旧的 torch 1.11 + cu113，DocTr++ 使用 torch 1.5，DocShadow 使用 torch 2.0 时代的配置。如果直接把某个仓库当作主工程，很难同时保证 CPU 可用、Windows 中文路径稳定和低显存运行。所以我保留了 `third_party/` 做方法来源和对照，但主包 `src/docrestore/` 按本机环境重新设计：NumPy/OpenCV/SciPy 处理主流程，PyTorch 只作为可选对照。

## 为什么光照估计默认用形态学闭运算

我最初把 guided filter 作为默认值，因为它的边缘保持性看起来更合理。但 20 对真实配对文档的对照显示，形态学闭运算在全图 PSNR、SSIM 和 RMSE 上都最好：18.989 dB / 0.843 / 0.127，guided 为 18.875 dB / 0.842 / 0.129，contrast-guided 为 18.888 dB / 0.842 / 0.129。差异不大，但形态学实现更简单、CPU 时间也最短。因此默认值改成了 `morphological`，guided 和 contrast-guided 保留为更平滑的备选。

## 为什么边缘保护和锐化默认关闭

第一轮实验里我假设“保护文字边缘一定更安全”，把 `edge_protection` 设为 0.72，并默认做轻微锐化。消融却给出相反结果：关闭边缘保护和锐化后，PSNR 从约 17.05 提高到 18.35，SSIM 也上升。我随后对 4 个保护强度和 3 个锐化强度做了 12 组扫描，最优组合是两者都为 0，PSNR 18.350、SSIM 0.827。原因是这个掩膜不只能识别笔画，也会保护阴影边界，导致阴影残留。真正需要恢复模糊文字的场景仍可打开锐化，但不适合作为所有文档的默认行为。

## 为什么彩色增益只作用于低饱和度纸面

如果直接对 RGB 三个通道全局除以背景光照，彩色阴影确实可能被压平，但印章、红头文件和彩色笔迹也会被漂移。我改为先做亮度增益，再估计三通道彩色背景；彩色增益只在低饱和度、较亮的纸面区域内混合。20 对数据的消融显示，关闭彩色校正只让 PSNR 提高约 0.03 dB，但这个损失很小，换来的是更符合彩色文档的任务边界。

## 为什么最终基准用的是 Jung 20 对而不是 SD7K

SD7K 官方 README 给的 OneDrive 数据集链接通过 API 返回 401，Hugging Face 搜索到的 `jsonjiao/sd7k` 和 `jsonjiao/sd7k_v1` 的第一行字段是 Stable Diffusion prompt、scheduler、latency 等，明显不是文档阴影数据。我不想下载一个同名但无关的数据集冒充结果。Water-Filling 仓库自带 20 对 Jung 真实配对图像，规模小、可直接校验，所以把它作为公开可复现的真实数据基准，并在报告中明确这不是完整 SD7K。

## 为什么默认关闭外观增强

反光、去噪、去模糊、褪色和划痕模块都实现了，但 Jung 这组图主要是阴影/光照问题。直接开启这些模块时，反光修复可能把高亮纸面误判为小反光，褪色增强也会改变原始对比度。最终消融显示“只用光照修复”的全图 PSNR 为 18.989，比开启外观增强的默认流水线更高。所以默认只修复光照，检测到对应退化的场景再用 `configs/scenarios/` 打开增强模块。
